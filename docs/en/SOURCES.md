# Data sources guide

**English** · [Español](../es/FUENTES.md)

Surimapa accepts two kinds of input:

| Input | Transport | Used for |
|---|---|---|
| **Suricata EVE JSON alerts** | Redis list `REDIS_KEY` (default `suricata`), one JSON record per element, pushed with `LPUSH` | Map, KPIs, rankings, event table |
| **pfSense firewall blocks** (`filterlog`) | Syslog over UDP (RFC 3164) to `NAS_LAN_IP:5140` | Firewall layer and card |

Anything that can **LPUSH an EVE alert into Redis** works as a source: Suricata's native Redis output, a log shipper tailing `eve.json`, or your own script.

Status of each recipe below:

- ✅ **tested**: used in production by the author.
- 🧪 **untested**: based on official documentation and the formats Surimapa expects. Please report results in an issue.

All IPs are **examples**: `192.168.1.10` is the Docker host running Surimapa (`NAS_LAN_IP`), and `192.168.1.1` is the firewall (`PFSENSE_IP`).

---

## What Surimapa expects (EVE alert)

Only records with `"event_type": "alert"` are stored; everything else is discarded, so send **alerts only** to save bandwidth. Minimum fields:

```json
{"timestamp":"2026-01-31T12:00:00.000000+0000","event_type":"alert",
 "src_ip":"203.0.113.5","src_port":4444,"dest_ip":"192.0.2.10","dest_port":22,"proto":"TCP","in_iface":"eth0",
 "alert":{"signature_id":2001219,"signature":"ET SCAN Potential SSH Scan","category":"Attempted Information Leak","severity":2}}
```

Handling of the record:

- **Optional fields:** `flow_id`, `app_proto` and `alert.action`.
- **Dropped fields:** `payload`, `payload_printable`, `packet` and `http` are removed before storing. Disable them at the source anyway, to save bandwidth and avoid shipping packet contents over the LAN.
- **Size and cleaning:** text is truncated, control characters are removed, and the stored raw JSON is capped at 4 KB.

Test the pipeline by hand from any machine in the LAN. The anonymous Redis user may `LPUSH`:

```bash
redis-cli -h 192.168.1.10 LPUSH suricata '{"timestamp":"2026-01-31T12:00:00.000000+0000","event_type":"alert","src_ip":"203.0.113.5","src_port":4444,"dest_ip":"192.0.2.10","dest_port":22,"proto":"TCP","in_iface":"eth0","alert":{"signature_id":2001219,"signature":"ET SCAN Potential SSH Scan","category":"Attempted Information Leak","severity":2}}'
```

Within a second it appears in the event table (use a real timestamp if you want it inside the default 24 h view).

## 1. pfSense + Suricata package ✅

Tested with pfSense CE 2.9 and the Suricata package 7.0.x (engine 8). GUI labels can vary slightly between versions.

### 1.1 Alerts: EVE → Redis

*Services → Suricata → Interfaces*, edit the interface (usually **WAN**) → section **Logging Settings / EVE Output Settings**:

1. ✔ **EVE JSON Log**.
2. **EVE Output Type**: `REDIS`.
3. **Redis Server**: `192.168.1.10` · **Port**: `6379`.
4. **Redis Mode**: `List (LPUSH)` · **Redis Key**: `suricata` (= `REDIS_KEY`).
   The package has **no Redis password field**. That's why Surimapa's Redis gives the anonymous user permission to `LPUSH` only.
5. **EVE Logged Info / Traffic**: keep **Alerts** only.
   - Uncheck HTTP, DNS, TLS, Files, SSH, SMTP, Flow, NetFlow, Stats, Drops, DHCP, MQTT, QUIC…
   - Uncheck **alert payload / packet** logging.
6. **Save**, then restart Suricata on that interface.

Notes:

- On the WAN of a PPPoE line, Suricata runs on `pppoe0` and sees traffic **after NAT**. Put your public IP in `WAN_IPS`.
- In **Legacy** blocking mode, pfSense (not Suricata) blocks the offender, so EVE always reports `"action":"allowed"`. Surimapa does not interpret that field as "blocked / not blocked".
- You can also enable EVE → Redis on a LAN instance: its alerts will show up with that `in_iface` (e.g. `bridge0`), and the interface filter can separate them.
- Traffic generated by pfSense itself does not pass through the interface rules, so a rule blocking port 6379 from other segments (VPN, VLANs) does not affect Suricata.

### 1.2 Firewall blocks: `filterlog` → syslog

*Status → System Logs → Settings*:

1. **General Logging Options**:
   - **Log Message Format** = `BSD (RFC 3164, default)`.
   - ✔ **Log packets matched from the default block rules in the ruleset**.
2. **Remote Logging Options**:
   - ✔ **Enable Remote Logging**;
   - **Source Address**: your **LAN** interface, so that the source is `192.168.1.1` = `PFSENSE_IP`;
   - **IP Protocol**: `IPv4`;
   - **Remote log servers**: `192.168.1.10:5140`;
   - **Remote Syslog Contents**: check **only** ✔ *Firewall Events*.
3. **Save**. No restart needed.

Surimapa stores one row per packet **blocked or rejected, inbound, on `FW_IFACE`, from a public IP**. Everything else is counted and discarded. Check the collector heartbeat (`fw_stored`, `fw_discarded_*`), see [DEPLOYMENT.md §6](DEPLOYMENT.md#6-verify).

## 2. Standalone Suricata on Linux (native Redis output) 🧪

Suricata can write EVE directly to Redis if it was built with **hiredis**:

```bash
suricata --build-info | grep -i redis      # must show "hiredis support: yes"
```

In `suricata.yaml`, add (or adapt) an `eve-log` output:

```yaml
outputs:
  - eve-log:
      enabled: yes
      filetype: redis
      redis:
        server: 192.168.1.10
        port: 6379
        mode: lpush            # "list" is an alias of lpush
        key: suricata          # = REDIS_KEY
      types:
        - alert:
            payload: no
            payload-printable: no
            packet: no
            metadata: yes
```

Restart Suricata (`systemctl restart suricata`). You can keep your normal file-based `eve-log` output as well: outputs are independent.

Set `WAN_IPS` if the sensor sees your public IP (a sensor on the router WAN after NAT).

### 2.1 Suricata in Docker next to Surimapa 🧪

If your router can **mirror a port** (SPAN), or the Docker host sees the traffic you want to inspect, you can run Suricata in a container. Example with the community image `jasonish/suricata`:

```yaml
services:
  suricata:
    image: jasonish/suricata:latest
    network_mode: host
    cap_add: [NET_ADMIN, NET_RAW, SYS_NICE]
    command: -i eth1                    # interface that receives the mirrored traffic
    volumes:
      - ./suricata/etc:/etc/suricata    # edit suricata.yaml here (§2) after the first run
      - ./suricata/log:/var/log/suricata
    restart: unless-stopped
```

Then check `--build-info` inside the container, enable the Redis `eve-log` of §2, and update the rules (`docker compose exec suricata suricata-update`).

## 3. Any Suricata that writes `eve.json` → Vector → Redis 🧪

If the sensor cannot write to Redis, ship its `eve.json` with [Vector](https://vector.dev), running on the sensor or on a host that can read the file:

```toml
# vector.toml
[sources.eve]
type = "file"
include = ["/var/log/suricata/eve.json"]

[transforms.alerts]
type = "filter"
inputs = ["eve"]
condition = 'contains(string!(.message), "\"event_type\":\"alert\"")'

[sinks.surimapa]
type = "redis"
inputs = ["alerts"]
endpoint = "redis://192.168.1.10:6379/0"     # anonymous user: LPUSH only
key = "suricata"
data_type = "list"
list_option.method = "lpush"
encoding.codec = "text"                       # sends the original JSON line
```

The same idea works with Fluent Bit, Filebeat or a small script: one alert per `LPUSH`.

## 4. OPNsense 🧪

OPNsense runs Suricata (*Services → Intrusion Detection*) but has **no Redis output** in the GUI. Suggested path: **syslog → Vector relay → Redis**.

1. *Services → Intrusion Detection → Administration → Settings* (advanced): enable **eve syslog output**. OPNsense then sends each EVE record to syslog.
2. *System → Settings → Logging / Targets*, add a target:
   - Transport `UDP(4)`;
   - Applications: `suricata`;
   - Hostname: the Vector host;
   - Port `5514`;
   - leave **rfc5424** unchecked.
3. Run Vector with a syslog source that keeps only alerts and pushes the JSON part to Redis:

```toml
[sources.opnsense]
type = "syslog"
address = "0.0.0.0:5514"
mode = "udp"

[transforms.eve]
type = "remap"
inputs = ["opnsense"]
source = '''
msg = string!(.message)
i = find(msg, "{")
if i < 0 || !contains(msg, "\"event_type\":\"alert\"") { abort }
.message = slice!(msg, i)
'''

[sinks.surimapa]
type = "redis"
inputs = ["eve"]
endpoint = "redis://192.168.1.10:6379/0"
key = "suricata"
data_type = "list"
list_option.method = "lpush"
encoding.codec = "text"
```

**Firewall blocks from OPNsense.** OPNsense also logs with `filterlog` using a very similar CSV layout. It may work if you:

- send the *filter* application to `192.168.1.10:5140` (UDP, RFC 3164);
- set `PFSENSE_IP` to the OPNsense IP;
- set `FW_IFACE` to its WAN device (e.g. `igb0`, `vtnet0`, `pppoe0`).

This is untested. Check `fw_discarded_malformed` in the heartbeat.

## 5. UniFi (Ubiquiti) gateways 🧪

UniFi gateways (UDM, UDR, UCG, UXG…) run Suricata for their built-in **IDS/IPS**, but:

- they do **not** expose EVE JSON or a Redis output;
- their syslog / SIEM export (*Settings → Control Plane → Integrations* or *System Logs → SIEM Server*, depending on the version) sends events in a **UniFi-specific or CEF text format**, which Surimapa does **not** parse;
- files inside the gateway can change with each firmware update, and custom software there is not supported by Ubiquiti.

Recommended options, from most to least robust:

1. **Run your own Suricata sensor** (§2.1) on a mirrored port of a UniFi switch (*port mirroring*) or on a host that sees the WAN traffic, with the native Redis output. This gives full EVE alerts and works with any router.
2. **Relay and convert** the UniFi syslog with Vector (§4) into the EVE fields listed in [What Surimapa expects](#what-surimapa-expects-eve-alert): `timestamp`, `event_type: alert`, `src_ip`, `dest_ip`, `proto`, `alert.signature_id`, `alert.signature`, `alert.category`, `alert.severity`. The mapping depends on the exact message format of your firmware; start from a captured sample.
3. *(Advanced, unsupported)* Read Suricata's own `eve.json` on the gateway over SSH, if your firmware keeps one, and ship it with the Vector recipe of §3. Expect it to break on updates.

Firewall blocks from UniFi are not supported: the format is not `filterlog`.

## 6. Other routers and firewalls

| Device | Suggested path |
|---|---|
| **IPFire** | Suricata writes `eve.json` → §3 (Vector) |
| **OpenWrt** | `suricata` package if your hardware can run it: native Redis output (§2) if built with hiredis, otherwise §3 on another host via syslog |
| **MikroTik RouterOS** | No Suricata. Mirror traffic (port mirroring or **TZSP sniffer**) to a Linux host running Suricata (§2.1) |
| **Firewalla, ISP routers, others** | Mirror or tap the traffic to your own Suricata sensor (§2.1) |
| **Security Onion, SELKS, Malcolm** | They already produce `eve.json`: ship alerts with §3 |

General rule: if the device can **mirror traffic**, run your own Suricata; if it can **send EVE JSON over syslog**, use a Vector relay; if it can **write EVE to Redis**, point it to Surimapa directly.
